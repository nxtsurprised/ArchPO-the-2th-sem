# Паттерны тест-кейсов для системы ГОСТ 34

Эта база знаний содержит повторяющиеся паттерны тест-кейсов для типовых функций системы.
Используй их как шаблоны при составлении тест-плана.

---

## Паттерн 1: Аутентификация пользователя

**Функция:** Вход в систему  
**Метод по ГОСТ:** Проверка  
**Предусловия:** Пользователь зарегистрирован, система доступна

**Шаги:**
1. Перейти на страницу входа `/login`
2. Ввести корректный email и пароль
3. Нажать кнопку «Войти»
4. Проверить: появился дашборд, в хранилище есть токен
5. Проверить заголовок: имя пользователя отображается

**Ожидаемый результат:** Пользователь авторизован, JWT-токен получен, перенаправление на дашборд.

**Доп. шаги (негативные):**
- Ввести неверный пароль → ожидать сообщение «Неверный email или пароль»
- После 5 неверных попыток → ожидать блокировку «Аккаунт заблокирован»

## Паттерн 2: Создание записи (CRUD Create)

**Функция:** Создание [шаблона / функции / подсистемы / документа]  
**Метод по ГОСТ:** Проверка  
**Предусловия:** Пользователь авторизован с правом `create_*`

**Шаги:**
1. Перейти в раздел соответствующих объектов
2. Нажать кнопку «Создать» / «Добавить»
3. Заполнить обязательные поля формы
4. Нажать «Сохранить»
5. Проверить: запись появилась в списке
6. Открыть запись, проверить сохраненные данные

**Ожидаемый результат:** Запись создана, данные сохранены без искажений.

## Паттерн 3: Ролевое разграничение доступа

**Функция:** RBAC — ограничение доступа  
**Метод по ГОСТ:** Тестирование  
**Предусловия:** В системе есть пользователь с ролью, у которой нет нужного права

**Шаги:**
1. Авторизоваться под пользователем с ролью без права `X`
2. Попытаться выполнить действие, требующее права `X`
3. Проверить: получен ответ 403 или действие недоступно в UI

**Ожидаемый результат:** Доступ запрещен, сообщение об ошибке корректное.

## Паттерн 4: Генерация документа (.docx)

**Функция:** Генерация ТЗ / ЧТЗ / ПМИ  
**Метод по ГОСТ:** Проверка  
**Предусловия:** Заполнен справочник функций, подсистем, ставок

**Шаги:**
1. Перейти к документу в нужном статусе
2. Нажать «Сгенерировать»
3. Дождаться завершения генерации (прогресс-бар или уведомление)
4. Скачать файл
5. Проверить: файл открывается, применены стили ГОСТ 2.105

**Ожидаемый результат:** Файл .docx создан, стили соответствуют ГОСТ 2.105.

## Паттерн 5: Многораундовое согласование

**Функция:** Согласование документа  
**Метод по ГОСТ:** Демонстрация  
**Предусловия:** Документ создан, оба РП зарегистрированы

**Шаги:**
1. ПМ: отправить документ на согласование
2. Проверить: документ заблокирован для редактирования
3. РП Заказчика: войти, открыть документ на согласование, нажать «Утвердить»
4. Проверить: ожидается решение второго РП
5. РП Подрядчика: аналогично — «Утвердить»
6. Проверить: раунд завершен со статусом «approved»

**Ожидаемый результат:** Документ согласован, статус изменен, история раундов сохранена.

## Паттерн 6: Проверка аудита

**Функция:** Журнал действий  
**Метод по ГОСТ:** Проверка  

**Шаги:**
1. Выполнить целевое действие (создать/изменить запись)
2. Открыть журнал аудита (суперадмин или раздел аудита)
3. Найти запись о действии
4. Проверить: зафиксированы actor, action, object_type, object_id, timestamp, diff

**Ожидаемый результат:** Запись в журнале аудита содержит все обязательные поля.

## Паттерн 7: НМЦК (.xlsx с формулами)

**Функция:** Расчет НМЦК  
**Метод по ГОСТ:** Проверка  

**Шаги:**
1. Перейти к документу НМЦК
2. Нажать «Сгенерировать»
3. Скачать файл .xlsx
4. Открыть в Excel/LibreOffice, проверить листы: Расчет, Справочник ставок, Сводка
5. Проверить наличие формул =SUM, =SUMIF (не значений)
6. Изменить ставку в Справочнике — пересчет в Расчете должен обновиться

**Ожидаемый результат:** Файл содержит формулы, пересчет работает при изменении ставок.
