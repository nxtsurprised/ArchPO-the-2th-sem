# Auth Service — отклонения от спецификации

## Что реализовано иначе

### 1. Сброс пароля — заглушка
**Спецификация:** `POST /api/auth/password/reset-request` + `POST /api/auth/password/reset-confirm` должны отправлять email со ссылкой.
**Реализовано:** `reset-request` всегда возвращает 200 (защита от перебора email), `reset-confirm` возвращает 400 `NOT_IMPLEMENTED`.
**Причина:** отсутствует SMTP/email-провайдер в MVP.

### 2. Хранение refresh-токена — хеш вместо значения
**Спецификация:** refresh-токены хранятся в БД.
**Реализовано:** в БД хранится SHA-256 хеш токена, а не сам токен.
**Причина:** дополнительная защита — утечка БД не даёт злоумышленнику использовать токены.

### 3. TOTP при логине — опциональное поле
**Спецификация:** TOTP обязателен если включён.
**Реализовано:** `totp_code` — опциональное поле в `LoginRequest`. Проверка производится в `auth_service.login_user` если у пользователя включён TOTP.
**Поведение:** если TOTP включён, но код не передан → 401.

### 4. Refresh-токен через httpOnly cookie (не тело ответа)
**Спецификация:** описывает передачу refresh через тело.
**Реализовано:** refresh передаётся только через `httpOnly; SameSite=Lax; path=/api/auth/refresh` cookie. В теле возвращается только `access_token` + `expires_in`.
**Причина:** защита от XSS — JS не может прочитать httpOnly cookie.

---

## Что добавлено сверх спецификации

- **`jti` в JWT payload** — уникальный UUID токена, зарезервирован для будущего blacklist (v2).
- **Структурированный JWKS** — `GET /.well-known/jwks.json` возвращает RFC 7517-совместимый JWKS с `kty`, `use`, `alg`, `n`, `e`.
- **Комментарии в коде** — каждое нетривиальное решение задокументировано inline (argon2id, side, httpOnly cookie, base64url).

## Что отложено (не реализовано в MVP)

| Функция | Статус | Комментарий |
|---------|--------|-------------|
| Отправка email (сброс пароля) | Заглушка | Нужен SMTP/SendGrid |
| Blacklist токенов через jti | Архитектурно предусмотрено | Нужен Redis |
| Consent management (GDPR/152-ФЗ) | Модель создана | API не реализован |
| Управление организациями / проектами | Не реализовано | Ответственность будущего Projects Service |
| rate limiting по IP | Middleware создан (`rate_limit.py`) | Не подключён к роутам |

## Известные ограничения

- `secure=False` в set_cookie — только для HTTP (localhost). В production нужно `True` (HTTPS).
- `JWT_ACCESS_TTL_SECONDS` = 900 сек (15 мин) — захардкожен в `.env.example`. Настраивается через переменную окружения.
- Пользователи создаются только через admin API — самостоятельная регистрация не предусмотрена (B2B-система).
