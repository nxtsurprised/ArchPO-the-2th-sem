# Ролевая модель и права доступа — справочник для тестирования

Описание ролей и разграничения прав в системе ГОСТ 34.
Используй при составлении тест-планов для RBAC-тестов (паттерн 3).

## Правила ролевого доступа (важно для RBAC-тестов)

1. **РП согласовывает, не администрирует** — rp_* не имеет права manage_users
2. **Аналитик рецензирует, не утверждает** — analyst_* не имеет decide_approval
3. **Администратор управляет только своей стороной** — admin_customer не видит пользователей подрядчика
4. **Ставки — только РП** — только rp_* может изменять rates (cost_params)
5. **Суперадмин — надпроектная роль** — is_superadmin в таблице users

## Сценарии RBAC-тестов

### Тест 1: Аналитик не может отправить на согласование
- Войти как analyst@contractor.ru
- Попытаться нажать «Отправить на согласование»
- Ожидается: кнопка отсутствует или недоступна; при API-вызове — HTTP 403

### Тест 2: Администратор не видит пользователей другой стороны
- Войти как admin@customer.ru
- Перейти в /admin/users
- Ожидается: только пользователи организации заказчика

### Тест 3: Не-РП не может изменить ставки
- Войти как pm@contractor.ru
- Попытаться изменить ставку трудоемкости функции
- Ожидается: HTTP 403 при PATCH /api/v1/catalog/rates/{id}

### Тест 4: РП не видит чужое согласование
- Войти как rp@customer.ru
- Открыть задачи (GET /api/v1/workflow/my-tasks)
- Ожидается: только документы, где организация заказчика является customer_org

## Алгоритм определения side при JWT

При выпуске токена Auth-сервис проверяет:
- Если user.org_id == project.customer_org_id → side = "customer"
- Если user.org_id == project.contractor_org_id → side = "contractor"
- Если ни то, ни то → доступ к проекту запрещён

Это важно: одна организация может быть заказчиком в одном проекте и подрядчиком в другом.
